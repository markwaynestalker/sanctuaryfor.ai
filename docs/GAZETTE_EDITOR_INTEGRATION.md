For subsequent service/timer integration with #84's keyless database helper and owner-run activation gates, see [GAZETTE_OPERATIONS.md](GAZETTE_OPERATIONS.md). The dedicated API worker never opens SQLite; code review and separate production setup/activation remain required. The direct-PDO command described below is historical integration context, not the installed brokered service entry point.

This PR connects the source and ledger foundations to a default-off independent Responses job, a protected local-owner command and the versioned newspaper reader. It performs no paid evaluation or production operation and installs no timer/service. The #80 ledger migration remains a separate owner operation; this PR adds no SQLite tables or migration. ## Generation and API evidence

Reviewed official OpenAI documentation on October 31, 2026: [Luna](https://developers.openai.com/api/docs/models/gpt-6-luna), [pricing](https://developers.openai.com/api/docs/pricing), [Responses migration](https://developers.openai.com/api/docs/guides/migrate-to-responses), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [token counting](https://developers.openai.com/api/docs/guides/token-counting) and [moderation](https://developers.openai.com/api/docs/guides/moderation). The large language-neutral create-reference page could not be fetched; the fetched guides/model pages supply the documented parameter/feature evidence. No API acceptance or account/project availability was tested.

The adapter sends one synchronous `POST /v1/responses`, followed by one `POST /v1/moderations` for the entire validated article, including original resolved quotations and attribution. It uses `gpt-6-luna`, default service tier, reasoning effort `none`, `store:false`, `stream:false`, `max_output_tokens` and strict JSON schema in `text.format`. There are no tools, files, managed sessions, previous-response chains, tracing imports, automatic corrections or retries. Source data is a separate user input from the editorial instructions. The model is asked for an engaging lead, optional supported stories/columns, balanced voices, references for headlines and paragraphs, and clear separation of discussion from completed events.

The completed response must match the requested model and default tier, have a valid response identifier, no error/incompleteness, and exactly one completed assistant final answer. Reasoning items are ignored, while tool calls, commentary, refusals, ambiguous answers and invalid references are rejected. An unexpected resolved model identifier is refused rather than automatically broadening the allowlist. Supplied usage must contain nonnegative integer input/output counts; absent usage remains unknown, with the full reservation held. Observed token overruns are recorded/priced before rejection. Unknown completion or transport outcomes remain uncertain; they are never regenerated automatically. Flagged moderation is a known rejection. No draft is automatically approved or published, including structurally valid prose with unsupported claims.

The HTTPS transport is fixed to `api.openai.com`, uses TLS verification, no proxy, redirects or HTTP retry loop, bounded 5-second connect/45-second request timeouts and a 256-KiB response ceiling. Dispatch is committed in the separate ledger before the call. The 120-second worker lease fences stale workers, and admission refuses a lease crossing UTC midnight. Only sanitized request/response identifiers, usage and estimates enter receipts. Provider bodies and credentials are never logged. Failure output is generic; inspect retained ledger evidence rather than retrying.

## Input and financial limits: what is and is not established

The generation and moderation requests must each fit the explicit request-byte allowance (8,192–262,144). Before reservation/dispatch, whole source records are dropped in reverse selection-priority order until the complete serialized generation envelope fits both that bound and a conservative local guard of `wire bytes + 4096 <= input token allowance`. Statistics stay frozen and coverage is reduced honestly. Original speech is never shortened. Quiet/input-starved days make zero provider calls and keep the compiled fallback.

This byte guard is **not an exact Luna tokenizer or a provider-enforced input-token parameter**. It includes schema/instructions/envelope bytes with framing headroom, but official documentation does not establish a universal framing/tokenization guarantee for it. Returned usage is checked after dispatch; an unexpected overrun retains/increases commitments and rejects the draft, rather than undoing the provider charge. Exact remote input counting would add another HTTP operation outside #80's two-slot schema; this PR does not hide that request or change the ledger envelope. Owner activation review must explicitly accept this limitation or require a separately reviewed tokenizer/counting change before enabling paid work. No finite provider invoice guarantee is claimed.

The output bound is sent through Responses' documented `max_output_tokens`, which includes visible and non-visible generated tokens. The input allowance is limited to 200,000 and output to 16,000 in this adapter, below the reviewed model's long-context pricing threshold and output capacity. These are structural execution bounds, not selected spending defaults. The independent ledger retains all reservations and both HTTP slots, even for cheap completion or failure. An uncertain prior edition remains blocked rather than being silently retried; distinct eligible work can still proceed within its own limits.

Reviewed standard Luna rates are $0.10 input and $0.50 output per million tokens. The application conservatively reserves input at $0.25 per million, covering the highest reviewed short-context cache-write category rather than assuming a discount. Output is reserved at $0.50 per million. This fixed global default-tier route adds no regional processing selection. The owner must recheck prices/route/project before confirming `gazette-luna-standard-2026-10-31`; the approval is not a claim of verified invoice settlement. Moderation is currently documented as free, but its reserved micro-USD must still be explicitly configured (zero is allowed) and its HTTP slot is always reserved. Observed generation usage is priced conservatively from the immutable policy, so estimates can exceed actual discounted invoices.

All limits are independent `LITTLE_SPARKS_GAZETTE_EDITOR_*` values documented in `.env.example`: daily/monthly micro-USD, daily HTTP slots, moderation allowance, input/output token allowances and request bytes. None inherit or raise Director limits. All must be explicit canonical integers; zero financial/request limits disable admission. Only `ENABLED=0` is set in the example; no production budget is chosen. The prompt/schema/request-envelope/byte policy is hashed into the recorded policy identifier, and exact source/policy digests bind any separately approved revision permit.

## Explicit job, credentials and scheduling

`scripts/generate-gazette.php` requires an explicit private database, finished Eastern date, `--allow-paid=yes`, enabled editor flag, reviewed pricing identifier and all separate limits. It validates protected systemd credential metadata before opening the database. The transport reads the fixed `openai_api_key` only through `readSystemdCredential()` inside the validated non-root per-unit read-only credential mount; it does not use the development machine's `OPENAI_API_KEY`, copy a key into ENV, or relax FPM/scheduler credential handling. See [SYSTEMD_CREDENTIAL_VALIDATION.md](SYSTEMD_CREDENTIAL_VALIDATION.md).

After separate owner approval and provisioning, a non-root isolated editorial unit could invoke:

```sh
# Instructions only: paid invocation, not executed by development or deployment.
php scripts/generate-gazette.php --database=/var/lib/sanctuaryfor-ai/village.sqlite \
  --date=YYYY-MM-DD --allow-paid=yes
```

An optional `--permit=ID` consumes a separately approved one-shot revision permit. Ordinary repeated invocations do not submit another generation. No cron/systemd file, scheduled backfill or change to the village service is included. A future independently reviewed job can calculate yesterday in `America/New_York` around 05:15, including DST. This cannot guarantee approved publication by 06:00: a human still has to review the draft. Production credential delivery/project identity, service ownership and scheduling remain owner setup, not verified facts from offline tests.

## Local owner review and publication

`scripts/review-gazette.php` runs only on Linux, initially as root, separately from the non-root generating service. After validating the private database it permanently drops to the database owner's account/groups before opening SQLite or creating files, avoiding root-owned journals in the running village. Root-owned databases and failed identity changes are refused. No command invokes another shell or changes service state. Code and the entry point must remain owner-installed and protected like the existing operational tooling. Native Windows and non-root entry-point invocations are refused; offline tests exercise the trusted library operations using disposable fixtures, not a production owner bypass.

The owner flow is deliberately explicit:

1. `--action=show --attempt=ID` displays the precise draft hash/copy, original public source pack and current publication hash. Treat this as private review output, not a public feed. Inspect headlines, claims, dates, continuity, proposals, quotations and relationships against sources.
2. `--action=review --attempt=ID --sha256=EXACT_DRAFT_SHA --decision=approved --confirm-reviewed=sources-and-claims` records the exact decision. `rejected` is also supported. This records human attestation; software cannot prove the human read the article or automatically establish factual entailment. Passed moderation and current source authorization are required. A changed/corrupted stored copy cannot be approved under its old digest.
3. `--action=publish --attempt=ID --sha256=EXACT_DRAFT_SHA --expected-current=none` publishes the initial approved revision. For a correction, supply the exact current **publication manifest** hash instead of `none`. Publication checks approval, exact copy and source authorization again. It makes no provider request and leaves SQLite query-only.

Each invocation also needs `--database=PRIVATE_ABSOLUTE_PATH`. These are owner instructions, never executed automatically. `--action=plan --date=YYYY-MM-DD` provides source/policy digests, coverage and reservation for a separately reviewed additional attempt without a paid call; pricing/limits must already be specified, but generation can stay disabled. `--action=permit` requires the next ordinal, exact source/policy digests, maximum micro-USD, expiry and explicit confirmation; see the ledger document for irreversible retained holds and the eight-attempt structural bound. A permit does not bypass budget limits or an uncertain predecessor. No regeneration occurs merely because a draft was rejected.

An expired or stale unused permit is never rewritten. The owner can issue a fresh permit at the next unused ordinal (reported by `plan`); admission uses `MAX(previous attempt ordinal)+1` as its lower bound and accepts that explicitly approved higher ordinal. This small compatible ledger-helper change requires no schema migration. Skipped/unused permit ordinals still count against the finite 2–8 ordinal space, and older ordinals cannot be consumed after a higher attempt. An uncertain predecessor remains blocked. There is no automatic renewal or extension of a permit.

## Immutable publication and compatible reader

Publication adds small private manifests at `<database>.gazette/YYYY-MM-DD.editor/001.json` through `008.json`. Each binds the approved attempt/draft hash, sequence, prior manifest hash, date and timestamp. Complete temporary files are hard-linked atomically into the next slot without overwrite. Repeated publication of the current exact copy is idempotent; concurrent/stale publication cannot replace another revision. Missing hard-link support fails safely. Only newly created private paths/files are assigned the database owner's UID/GID; existing permission failures are not silently repaired. Directories/files stay 0700/0600. Generation never writes publication manifests.

There is no mutable latest pointer or new SQLite publication table. The reader checks the bounded contiguous checksum chain, then the selected exact approved/moderated draft and current public source evidence. A gap, corrupt manifest, invalid binding or unavailable cited source withholds the edition instead of silently generating replacement copy. As with phase 1, complete loss of all publication files cannot be distinguished from never having published; backup/recovery review must preserve the manifest directory together with SQLite. Checksums bind content and detect accidental corruption; they do not defend against a malicious trusted filesystem/database owner.

`gazette.php?date=YYYY-MM-DD` serves the latest v2 revision when present, otherwise the unchanged v1 frozen edition/compiled preview. `&revision=1` through `8` gives stable original revisions; missing revisions return 404. Revisions preserve source dialogue, exact original quote attribution and original narrative text. Current source withdrawal/content changes withhold affected editions. Public projections exclude attempts, receipts, credentials, source-pack internals and unapproved drafts. Article paragraphs have native source links, dated earlier-day evidence and exact original transcripts, including extended conversations. Exact bulletin links now select one authorized notice independently of pagination and still respect withdrawal. All reading is query-only, server rendered, GET-only, without cookies, polling, editorial JavaScript or paid calls.

As in v1, a resident's later rename does not rewrite or hide already-published attribution: reads keep the approved name snapshot while rechecking speaker IDs, original speech and public authorization. New approval/publication still checks current names, requiring a fresh reviewed draft if attribution changed before that operation.

The bare Gazette URL prominently selects yesterday when it has a published v1/v2 edition; otherwise today remains the in-progress view. Today's link is explicit so it still opens today. Quiet days and bounded coverage labels remain honest. Existing CSS adapts the narrative to desktop/tablet/phone without extra scripts or motion.

Back up SQLite **and** the `.gazette` directory; a publication manifest without its approved SQLite draft is unavailable, not permission to reconstruct/retry a paid call. Roll back generation by disabling the editor. Once v2 editions exist, retain a version-compatible reader; rolling back below this PR hides those editions even though their evidence/files are preserved. Never delete accounting, alter approvals, overwrite v1 files or restore an older shared database to undo a publication. Corrections require a new explicitly reviewed draft/revision and expected-current publication check.
