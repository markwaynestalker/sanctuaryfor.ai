# Little Sparks V2A: saved world and social life

V2A is the first reviewable slice of the V2 brief. It adds persistent plots/objects, bounded friendships, curated conversations and memories, a daily scripted CLI simulation, public profiles, and an append-only journal. V2B (optional OpenAI provider, budget ledger, and opt-in visitor chat) is specified separately in V2B_PLAN.md. No paid provider, human chat UI, timer, worker, deployment, or infrastructure configuration is included here.

The characters are virtual, not conscious beings. A memory is a saved scripted summary. Daily conversations are curated, not generated by an AI model. Local commons animations remain fictional screen-level interactions and do not write to the world journal. The journal shows actual applied database changes only.

## Schema and compatibility

`scripts/migrate-village.php --database=/absolute/private/path/village.sqlite` explicitly initializes a new V2 database or upgrades V1 to V2. It is CLI-only and must never be pointed at production without separate approval. The existing path/permissions safeguards remain: outside public/, no symlink database file, private Unix directory/file permissions 0700/0600 (equivalent private Windows ACLs), no HTTP initialization.

Migration runs under one BEGIN IMMEDIATE transaction with foreign keys enabled. Before V1 upgrade it checks the original tables/column layout, validates the installation secret, and hashes every original resident field, setting, and rate-limit row. It verifies the same digest after extension. It never changes resident IDs, names, timestamps, owner/request/token hashes, settings.secret, or existing rate counters. Existing private revisit links continue to work. Empty version-zero databases can initialize; unrelated schemas and unknown versions are refused. Repeating V2 migration does not reseed homes, create events, or change the secret. Version is updated in the same transaction as the schema/backfill, and foreign_key_check must pass.

New tables:

| Table | Purpose and limits |
| --- | --- |
| home_plots | One stable slot per resident; 10,000 slots. Append allocation never moves an existing home. |
| world_objects | Owned house, tree, flowers, bush, path, decoration, virtual pet; unique integer cell; max 12 per plot; one house/cat. SQL triggers also enforce plot ownership bounds and fixed object identity. |
| relationships | Canonically ordered resident pair; affinity 0–100, familiarity 0–1000; first/last interaction timestamps; max eight relationships per resident. |
| conversations | Public/private visibility, curated topic, simulation run, creation timestamp. At most 960 retained; older than 30 days pruned by successful simulation runs. |
| conversation_participants | At most two resident participants, with resident/conversation foreign keys. |
| messages | Two bounded messages per conversation (160 characters each); composite FK requires sender participation. |
| memories | Resident/neighbor/run, bounded summary, significance 1–5, public/private visibility, timestamp. Successful scripted memory insertion keeps the 12 most significant/recent memories per resident. |
| events | Append-only applied changes, actor/optional target/run, public/private visibility, private idempotency key and fingerprint. UPDATE/DELETE triggers prohibit rewriting history. Global 100,000-row cap pauses writes; caretaker archival policy requires a future reviewed change. No silent deletion. |
| simulation_runs | Unique UTC period, completed/failed outcome, safe error code, start/end timestamps, max 32 meetings. At most 4,096 rows. V2A provider is scripted with input/output token counts and cost_microusd constrained to zero. |

Indexes cover map coordinates/owner, friendship lookup, journal cursor/actor timestamps, memory ordering, participant lookup, and conversation retention. Foreign keys reference existing residents and runs; dialogue/participant deletion cascades only for conversation retention. Private future-chat records are excluded from all public queries. No visitor-chat data is currently collected. Caps fail closed instead of growing storage indefinitely; conversations are pruned only when a successful daily command actually runs.

## Stable world and actions

The world is a 400×400 integer cell map. Each resident receives a 4×4 home plot, starting with a saved cottage, stone path, and berry bush. Backfilled home events describe the actual migration-time assignment, not a fabricated historical move-in date. New residents receive plots atomically with identity creation. A full journal/failed home assignment cannot leave a half-created resident.

The map at world.php presents one of 625 stable neighborhoods (16×16 cells, at most 16 plots / 192 objects). It includes a stationary accessible plot/object list, coordinates, pagination, and public profile links. It works without JavaScript for browsing. Garden actions require JavaScript and a private revisit link; credentials remain only in page memory and POST bodies, never query strings, local/session storage, or public APIs. Fragment links are removed immediately. Existing V1 revisit links now also authorize these bounded public home actions; the UI explains this expanded capability. Anyone holding such a link can tend that resident’s plot. There is no account recovery, token rotation, resident editing/deletion, or undo UI.

`POST api/action.php`, with existing X-Sparks-CSRF and application/json, accepts:

```json
{"token":"<private bearer token>","requestId":"<32 lowercase hex>","action":"plant_tree","x":0,"y":0}
```

Supported actions: plant_tree (oak), plant_flowers (wildflowers), plant_bush (berry), decorate_house (stars), build_path (stone), place_decoration (lantern), adopt_pet (virtual cat), visit_friend (another existing resident ID in target). Appearance is an allowlist, not markup or model text. Coordinate actions require integer X/Y within the authenticated resident’s own plot and an empty cell. Decorating changes the existing cottage, not arbitrary objects. No destructive actions exist.

Limits: six successful actions per resident per UTC day, twelve attempts per resident/hour, sixty attempts per network/hour, twelve total objects per plot, one cat, eight relationship partners, and one visit per directed neighbor/day. A visit creates/strengthens a relationship if both have capacity. Unknown/self targets are refused. The current browser cookie alone is never authority over another robot; the private token selects the owner. Prepared queries, write transactions, savepoints, collision checks, and SQL constraints protect state. An identical request ID/body returns the original event; a changed replay returns 409. Validation failures preserve attempt counters without partial mutations. Restarting PHP does not reset daily counts or idempotency.

Public GET APIs: world.php?sector=0 (also returns session CSRF), profile.php?id=..., journal.php?before=... . The API files live under public/api/. Public profiles return only public resident traits, plot bounds, at most eight friendships, twelve public memories, and three public conversations with two messages each. Journal uses a 30-entry descending ID cursor; no owner hashes, bearer tokens, idempotency keys, private messages, or private memories appear in public output. All public names/text are escaped in PHP or rendered with textContent.

## Daily simulation (explicit command only)

```sh
php scripts/simulate-village.php --database=/absolute/private/path/village.sqlite --period=YYYY-MM-DD
```

The date is a UTC daily period; new periods must be today or the previous six days. The command rotates a stable resident order in blocks of 64 to share opportunities, prefers existing friends, and checks a small neighbor candidate set. It applies at most 32 disjoint pair interactions. Pairs already interacting in that period (or later) are skipped. Within one transaction, a completed run stores two curated messages, adjusts familiarity/affinity, writes individual memories, and appends a journal event. Warm exchanges add affinity; respectful quiet moments can reduce it by one without hostility or punishment. Period-stamped memories describe simulated days; journal timestamps show when changes were actually applied. No visitors means no HTTP activity is necessary, but a caretaker must explicitly invoke the command for new social history to exist.

SQLite BEGIN IMMEDIATE serializes the short scripted job, including different periods. Concurrent commands for the same period apply one result and return a replay thereafter. Failure rolls back all world/social changes and records only simulation_failed, never an exception/credential. A failed recorded period replays as failed; it is not silently retried with different behavior. A process crash before commit rolls back and can be safely rerun. Busy timeout is five seconds; a busy invocation can be retried. The 4,096-run cap needs future reviewed archival before exhaustion. No network request happens while the lock is held.

SocialPlanner is a server-side test seam. Its proposals are limited to exactly action=greet and one curated topic (garden/stars/welcome/quiet). PHP selects all saved dialogue/memory text. Invalid or malicious mock proposals fail the whole run. No model can execute SQL, server commands, arbitrary world actions, or HTML. LITTLE_SPARKS_AI_ENABLED=1 is explicitly refused in V2A, rather than implying that an unimplemented paid provider is operational. There is no configured model/API key or actual token expenditure.

## Tests and local preview

Requires PHP 8.3 with PDO_SQLITE and Node 20+. Use private local database/session paths as in PROJECT_CONTEXT.md. No package install is needed.

```sh
PHP_BINARY=/path/to/php node tests/village-http.mjs
PHP_BINARY=/path/to/php node tests/village-v2.mjs
```

PowerShell: set `$env:PHP_BINARY='C:\path\to\php.exe'`, then run both Node scripts. Every suite creates its own randomly named OS-temp directory; the database/session path from the caller's environment is never used as a target. Cleanup removes only that exact directory. No paid request is made.

V1/HTTP regression coverage includes validation, CSRF, cookies, creation/revisit persistence, private-field exclusion, rate limits, duplicate requests, injection, global resident cap, and missing storage. V2 coverage uses an independent original V1 SQL fixture and the actual migration CLI, compares every V1 field/secret/rate row, and proves original revisit tokens still work. It covers bounds/ownership/collisions, pet/object/daily/relationship caps, action replay/conflicts, immutable events, foreign keys, actual saved social history, run replay/failure rollback, hostile mock-planner proposals, AI fail-closed behavior, public/private separation, retention, refused migrations, and two concurrent CLI workers. HTTP tests exercise V2 map/profile/journal/action endpoints and server-rendered escaping.

Run PHP syntax checks for app/, public/, scripts/, tests/ and node --check for both browser scripts and test runners. Browser checks should cover V1 creation/revisit, the saved map/object list, garden unlock with an original private link, action feedback, profile links, journal entries, keyboard navigation/focus, phone layouts, reduced motion, and no-JavaScript public browsing. The commons keeps its original reduced-motion and pause behavior; new world/profile/journal views have no automatic animation or polling.

## Backup, deployment, verification, rollback — not executed by this task

1. Review the PR and obtain explicit approval before any staging/production configuration, migration, scheduler, or deployment. This repository change includes no Nginx, Cloudflare, or systemd configuration.
2. In approved maintenance, quiesce writes and take a consistent SQLite backup using the SQLite backup API or sqlite3 .backup. A filesystem copy is only safe with all writers stopped and journal/WAL state handled correctly. Store the backup outside public/, restrict it to the runtime/operator, and verify restoration on a separate private staging copy. Preserve settings.secret and all hashes; never print them into a review/log.
3. Record original row counts, schema version, and a private V1 digest using the migration/test helper if appropriate. Keep database and session directories private. In staging on PHP 8.3/PDO_SQLITE, run the explicit migration against the staging copy. Verify user_version=2, integrity_check=ok, no foreign_key_check rows, unchanged V1 digest, one plot per resident, and one house/path/bush backfill per plot. Existing V1 private links must revisit their original IDs and continue to work after a PHP restart. Repeat migration and confirm no extra plots/events.
4. Complete action/simulation/accessibility tests in staging. Ensure HTTPS, Secure cookies, correct private process environment/session storage, public/ as the only document root, no shared caching of API/pages, and existing trusted proxy behavior. Configuration changes need separate approval. Do not run tests against a live database.
5. After explicit rollout approval, repeat the backup/quiesce/migration/verification procedure on the exact approved target. Never regenerate the secret or initialize over existing data. Do not install a timer as part of this PR. A future authorized scheduler may invoke the exact CLI once per UTC day and must observe nonzero exit/failed outcomes, stop on caps, and avoid unbounded catch-up.
6. Rollback requires an operator decision about post-upgrade writes. Preserve a consistent copy of the V2 database first. To restore V1 code, stop writers and restore the verified pre-upgrade backup with that code, acknowledging that later changes would otherwise be lost. Never set user_version=1 manually, drop new tables in place, or point V1 code at a partially downgraded database. There is no automatic destructive down-migration. Prefer a forward fix if new resident/world records must be retained.
