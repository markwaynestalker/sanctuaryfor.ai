# Configurable multi-message encounters (#74)

The Director chooses a natural stopping point within `LITTLE_SPARKS_CONVERSATION_MIN_MESSAGES` (default 2) and `LITTLE_SPARKS_CONVERSATION_MAX_MESSAGES` (default 16). Both accept canonical integers from 2 through 64, with minimum <= maximum. One message cannot represent an encounter between two speakers. Invalid, blank, fractional, overflowing or inverted settings refuse execution; there is no clamping. The absolute ceiling 64 bounds persistence, decoding and browser speech queues while allowing future increases through configuration. PHP does not load `.env.example`; owner-reviewed values belong in protected simulation configuration.

The maximum is a safety limit, never a target. Fresh context and structured output guidance allow brief exchanges, disagreements, humor and unresolved endings without padding. Strict A/B alternation begins with the first selected participant; either can finish, including odd lengths. This keeps attribution and the existing two-participant encounter model clear. It does not mean both speakers must agree. Each original message still has the existing 1–160 Unicode-character validation, with complete-sentence/100–130-character guidance. No words are rewritten, shortened, padded or regenerated.

## Storage and compatibility

The existing V6 tables constrain messages and note sequences to 0/1. An explicit transactional add-on creates `conversation_message_meta`, `extended_conversations`, `extended_messages`, `extended_director_notes` and `conversation_attempt_contracts`. Existing tables, rows, public IDs, credentials and `user_version=6` are preserved. No historical transcript is backfilled or rewritten. Extension guards enforce contiguous sequences, the declared count, actual participants, alternating attribution, immutable history and no overlap with legacy storage. The union message view exposes an extended transcript only when its declared count is complete.

Before installation, existing two-message v1 behavior remains compatible. After installation the application uses `sanctuary.director.v2` (or `sanctuary.director.bulletin.v2`) and stores the entire encounter in extension tables, even when the Director chooses two messages. Legacy attempt ledger contracts remain untouched; the additive attempt-contract row records the actual v2 contract in the same reservation transaction. Existing bulletin notice provenance retains its established v1 semantics. All public readers and source-authorized memory lookups use unified history. Archive search includes later messages. Transcript fetches are batched, never per message or per exchange.

Migration command, for a separately approved private, backed-up, drained V6 database:

```sh
php scripts/migrate-conversation-messages.php --database=/path/to/private/village.sqlite
```

This is an operational instruction, never invoked automatically by CI, deployment or a visitor request. Back up and verify integrity/FKs first; drain writers and pending opportunities under the existing owner procedure, review the exact release SHA and output budget, then migrate and verify. Migration checks integrity/FKs inside its transaction. It neither enables AI nor changes timer/configuration. Development fixtures test rollback and preservation of every preexisting table definition and row.

Once extended history exists, old software cannot read it. Rollback therefore needs a compatible build that understands this add-on. Setting the range to 2/2 on compatible software limits new speech while preserving all extended history. Do not drop extension tables, delete sessions, restore an older database over current history/accounting, or roll back blindly to pre-feature code.

## Accounting, memory and scheduling

A complete exchange uses one bounded Director invocation and one moderation request covering the complete proposal/context. Managed inspection/polling/cancellation retain the existing eight reserved HTTP slots. There is no paid request per message. One exchange means one conversation, relationship affinity/familiarity increment, interaction count and fairness consideration. The existing opportunity interval (including production's five minutes), nighttime rest, cooldowns, deadlines, leases and replay fencing are independent of message count.

Notes can reference the actual later sequence and must quote original text from that exact message. Notes remain unverified preferences, interpretations or rumors; at most two per encounter and the existing resident quotas remain. Statements and proposed plans do not become facts or completed actions. Memory retrieval returns complete retained exchanges. The unchanged context byte limit may drop a whole optional exchange when longer transcripts do not fit; larger stored history does not promise that all history enters every request. No automatic summaries or extra memory model calls are introduced.

Session scope remains an unordered pair plus identity revisions, runtime and Director fingerprint. V2 additionally binds contract and message bounds so a reused session cannot retain a stale two-message schema or outdated maximum. Old session rows are preserved; no resets or hosted instruction edits occur. New and reused v2 encounters receive the current mandatory guidance.

## Output budget review

The additional [managed session spending review](MANAGED_SPEND_CONTROL_REVIEW.md) documents SDK `spend_control` support, conflicting reference variants, the earlier recorded rejection and cumulative-session implications. Provider spend enforcement remains an explicit unresolved activation-review item; this PR does not re-enable the field or change session rotation.

The legacy 512-token setting cannot support the maximum reliably. V2 refuses preparation unless `AI_MAX_OUTPUT_TOKENS >= MAX_MESSAGES*768+1024` (all settings have the `LITTLE_SPARKS_` prefix). This is a conservative application allowance for 160-character Unicode messages, JSON IDs/envelope and notes, not a promise of exact tokenizer behavior. Sixteen messages require at least 13312; isolated tests use 14000. Sixty-four require 50176. Owners must review an explicit allowance and its per-encounter reservation before activation. No daily/monthly cap or production ENV value is changed here.

Responses receives the configured `max_output_tokens` as a hard request parameter. The existing hosted managed-session create envelope has no corresponding supported hard output-token field in this integration; it remains schema/deadline bounded, and full application commitments stay conservatively charged. The output allowance is an accounting input, not a guaranteed managed provider bill cap. Managed live validation of longer generations is a separate approved staging check. Missing usage, cancellation uncertainty and historical commitments retain existing handling. Oversized/incomplete/ambiguous output or a rejected message anywhere prevents saving the whole conversation; no partial transcript is presented as complete.

Whole-exchange moderation also needs request capacity. V2 refuses before generation unless `AI_MAX_REQUEST_BYTES >= 2*MEMORY_CONTEXT_BYTES + MAX_MESSAGES*768 + 4096`. This reserves for JSON-escaping the fresh context, four-byte characters in every message, attribution and notes. At the default 8192-byte context and 16 messages, review at least 32768 request bytes; the legacy 16384-byte template is insufficient for this worst-case envelope. At 64 messages, the same formula requires 69632 bytes. No request-byte setting is raised automatically. Incoming proposal decoding separately permits twelve-byte surrogate escapes while preserving the 160-character rule and existing 256 KiB transport response ceiling.

## Reading and verification

The journal uses a native expandable transcript above four messages. Archive native links, profiles and the persistent commons panel retain every original line in order. Browser read-aloud starts only through an explicit button and uses an available on-device English voice; unsupported or remote-only voice environments keep the control hidden. There is no paid TTS or network request. Stop, hidden tabs, page exit and commons playback cancellation invalidate queued callbacks. Text remains readable without JavaScript or speech support. Physical iPhone Safari and installed voice availability remain owner device checks.

Development generation comparisons and their limitations are recorded separately in `docs/evaluations/multi-message-74.json`. No production data, configuration, scheduler or hosted definition is changed. Merge, migration, output-budget activation and deployment remain separately reviewed owner operations.

Six authorized synthetic Luna Responses generations compared one sample per arm in three scenarios. V1 returned 2/2/2 messages; v2 chose 4/3/2. All application and moderation checks passed. The disagreement developed a counter-response, the child scene continued an imaginative idea, and the repetitive-topic scene remained brief. Total observed input/output was 15430/952 tokens, with cached inputs and cache writes included in the approximately $0.00156066 estimate at [official pricing](https://developers.openai.com/api/docs/pricing), checked October 29, 2026. The precommitted local evaluation allocation was $0.10; no retries occurred. This is qualitative, small-sample evidence of useful variable length, not a measured general quality improvement. All six proposals had no memory notes, so they provide no evidence of improved long-term recall. Offline tests establish complete-history retrieval and later-sequence attribution; maximum-length hosted performance and physical-device speech remain separately reviewed staging/device checks.
