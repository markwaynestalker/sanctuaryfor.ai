# Personal Spark memory and independent replies

The owner requested a PR after reviewing #94 and asking why Sparks do not remember across partners like a continuous conversation. The owner subsequently clarified that quality, memory and independence matter more than minimizing token spend. This implementation does not shorten exchanges to fit the old eight-request managed ledger. It adds the accounting needed for the configured conversation length, while keeping accurate usage, explicit operational budgets and duplicate-dispatch protection.

## What changes

SQLite remains the authoritative history. A Spark's stable resident ID owns its perspective across partners and provider calls. No BigQuery migration, bulk upload, continuously running subprocess, separate model subscription or new hosted agent definition is required. The new `independent` mode is opt-in; the default `director` mode remains supported.

In independent mode, each Responses generation portrays one Spark and returns only its own reply, a request to recall an older experience, or a decision not to speak. The server supplies the other participant's actual preceding utterances. It does not ask a Director to invent both sides or replace the returned words. Each Spark receives its own identity, existing receipt-backed memories, attributed notes, legitimate personal history and shared exchanges; the counterpart supplies only a public ID/name and actual speech. The counterpart's description, goals, memories, unrelated experiences and operator ideas are not broadcast. Gazette stories and global Director continuity are omitted in this mode. Existing whole-exchange moderation receives the original complete proposal/context before any dialogue is public.

`sanctuary.spark.reply.v1` is an application protocol using Responses structured output, not OpenAI's subagent orchestration. `tools:[]`, `store:false` and no `previous_response_id` prevent a pair's hosted session context becoming a resident's private perspective. SQLite supplies durable experience and recall on each call; this does not claim that model weights learn, that a provider session is permanent memory, or that a Spark has human consciousness. Existing registry/model/credential protections still govern admission. Registered hosted Director instructions are untouched and are not used to author an independent Spark's speech; the reviewed local `sparkInstructions()` defines that protocol.

Independent mode initially supports dialogue/quiet only. World changes, notice posting, goal transitions, personality rewriting and durable confidences are outside this slice. Default Director world-action behavior is unchanged. Anger, refusal and unresolved disagreement are permitted without conflict quotas, forced apologies, lessons or joke bans. Message counts retain the configured 2-64 domain, strict alternation and 160-character ceiling. The maximum is never a target. Either Spark can stop further rounds; the counterpart's willingness cannot override that decision. An attempted exchange with fewer than the configured minimum accepted utterances becomes quiet instead of forcing more speech; incomplete single-person speech is never published as a two-person encounter.

## Durable memory and relevance

`sparkRecall` searches the holder's retained public conversations, applying partner/phrase conditions before the bounded candidate limit. It can therefore find an old shared disagreement beyond forty unrelated newer meetings. Lookup is literal, Unicode-caseless substring search, not semantic embeddings. The model may refine a search phrase. Results contain complete original episodes, dates, original labels, speaker names/IDs and message attribution; absent results do not authorize invented history. Defaults allow two recall requests per speaking turn, configurable from zero through eight via `SPARK_RECALLS_PER_TURN`; each lookup is local and its follow-up generation is accounted for upfront. Result/candidate counts retain existing memory configuration. An oversized mandatory result/core refuses safely rather than silently truncating it.

Fresh default-Director context also improves: shared pair history is retrieved separately so unrelated recent encounters cannot consume its entire selection window. Optional note retrieval scans bounded candidates past invalid sources and distinguishes the holder from the actual quoted speaker. Recent third-party history stays with its legitimate participant. Existing legacy labels, original speech, memory receipts and historical sessions remain unchanged. Input/session scope advances to `sqlite-v6-6`; no old session is reset or deleted.

Working dialogue is bounded by message/request/input limits, separately from the memory-byte allowance. Exact current and preceding speech and explicitly requested recall results are never silently dropped. Optional personal notes/history can be removed under byte pressure; source IDs for only actually supplied context are retained. During accepted persistence, all supplied episode hashes, current public provenance and holder membership are rechecked, then identifiers-only `spark_memory_context:RUN:RESIDENT` receipts commit with speech. They mean supplied context, not verified influence or belief. Invalidated sources roll back new dialogue, notes, lineage and relationship changes atomically. No new fact story or formal gossip receipt is fabricated. Memory does not depend solely on the finite quote-note quota: original accepted episodes remain searchable after note capacity is reached.

## Reader continuity

Journal and archive readers now offer native predecessor/root links for genuine continuation segments. A bounded batch validates target, predecessor and root with the archive's completed-run/event/actual-speaker authorization and matching pairs. Unavailable/private roots are omitted without revealing their identifiers. Original timestamps, separate encounters, labels and text stay intact; no transcript is rewritten or combined into a fictional encounter. Legacy V2-V4 readers retain their existing four-read journal budget. No browser polling or provider request is introduced.

## Accounting and concurrency

An explicit additive V6 migration creates three new tables: immutable capability revision `spark_memory_meta`, encounter reservation/finalization `spark_encounters`, and contiguous call intents/completion metadata `spark_calls`. It changes no old table or `user_version`, rewrites no historical ledger and creates no credential. Partial/unsupported capability refuses admission. Migration requires the existing backed-up/drained-writer procedure and integrity/FK checks; it is never executed by browsing, deployment or generation.

For maximum M messages and R allowed recalls per speaking turn, reserve M*(1+R) generation calls plus one full-proposal moderation call. At 16 messages/R=2 this is headroom for 49 calls, not 49 automatic dispatches. A natural three-message exchange without recall uses three generations plus moderation. Each intent is committed under the lease/write lock before dispatch. An unfinished call blocks another dispatch for that attempt. No automatic HTTP retry, historical replay, overlapping paid worker or resumed unknown turn is introduced.

The old parent ledger retains its two Responses slots; the new ledger records the additional reservation and a final adjustment for this new mode only. Pending/unknown work holds its entire reservation. Once all dispatched calls are known complete, unused new headroom closes and the daily total reflects actual calls, including a rejected response. Old managed eight-slot commitments and all historical uncertainty stay untouched. New zero-call rejection can close unused admission headroom without pretending a request occurred. Immutable completion guards bind the adjustment to actual contiguous call rows. A crashed/expired worker keeps full unfinalized headroom; diagnostics/reconciliation never replay it or release it automatically.

Each generation reserves the configured input allowance and a 1024-token reply output allowance, including reasoning. Complete usage/model/tier observations are validated per call and summed into the parent once known; no partial usage is substituted after a timeout or missing usage. Response IDs and aggregate token/cost estimates are retained without raw bodies, queries, private prompts or credentials. Actual estimates are not independent final billing evidence. `ai-status.php`, operational admission and optional reconciliation include new reservations and actual dispatch starts. The established explicit daily/monthly budgets and existing $1 per-attempt schema domain remain validated; there is no silent production increase or selected monthly ceiling.

## One reviewed rollout procedure

Development performs none of these production operations. After final review and exact-main Ubuntu CI:

1. Use the existing owner backup/drain/exact-SHA deployment procedure. Preserve the previous timer state, SQLite/private files, all Gazette policies, credentials, revisions and holds.
2. With the new code and writers drained, run `php scripts/migrate-spark-memory.php --database=/approved/private/village.sqlite`. Verify integrity/FKs and the installed capability. Existing public conversation storage is adopted unchanged; there is no historical backfill.
3. Review the independent-mode configuration once in the existing protected scheduler environment. Set `LITTLE_SPARKS_DIALOGUE_MODE=independent` and `LITTLE_SPARKS_DIRECTOR_RUNTIME=responses`. Keep the reviewed model/project/key and explicit daily/monthly budgets. Preserve the desired conversation range, e.g. 2-16. No per-edition/per-conversation approval is added. Current owner-written registry configuration must remain valid for Responses; an empty managed-only export cannot silently become Responses instructions. Resolve any such registration mismatch through the existing reviewed local registration path, without editing the hosted agent.
4. Review the execution envelope: independent defaults are 180 seconds plus 15 seconds reserved for finishing/moderation and a 210-second lease. Explicit old values are validated, never overridden. If setting them explicitly, review `DIRECTOR_RUN_SECONDS=180`, `AI_LEASE_SECONDS=210`, `AI_DAY_BOUNDARY_GUARD_SECONDS=210` (all prefixed `LITTLE_SPARKS_`). The optional owner-installed `ops/systemd/sanctuary-village-independent.conf` gives the existing service a 300-second outer timeout; it selects no mode, delivers no key, starts no service and enables no timer. Reload units through the owner runbook, drain before planned changes, then restore only the previous scheduler state. The five-minute interval/fairness/rest rules and existing no-overlap fences stay unchanged.
5. Run existing metadata-only scheduler/status checks first. Verify independent capability/mode, total planned headroom, configured message range, required timeout/lease, current budget and nonsecret credential delivery. Observe ordinary new opportunities only after owner activation. Compare call rows and actual token estimates with the intended OpenAI project. Do not generate a paid test, replay failed periods or reset old reservations implicitly.

For code rollback, retain a compatible reader/accounting build that understands the additive ledger; pre-feature writers do not count its commitments. Switching mode back to `director` on compatible code is allowed after draining, preserving all new/old commitments and records. Restore the prior runtime/configuration and unit envelope deliberately; never drop the tables or restore an old database over current history.

## Evaluation and limits

Offline fixtures establish holder boundaries, exact older recall, fresh/continuation context, 2/3/8/16 independent replies, stopping, anger, full moderation, byte pressure, actual costs/request counts, additive migration/rollback, source withdrawal, replay, daily caps, uncertain holds and real-process dispatch concurrency. Full offline suites and exact-commit Ubuntu CI, including existing real UID/systemd credential/socket isolation, are required. No hosted definition, production state, key or private trace was accessed; no paid calls were made. The November 13 deployed SHA, actual supplied contexts and hosted session histories remain unknown. The owner-reported examples are evaluation cases, not a verified causal diagnosis.

A separately authorized model comparison should freeze an isolated chronological history and compare three arms: current main; improved retrieval with one Director; independent Sparks with the same eligible history. Match identities, dates, model, scenario and opportunities. Advance each arm using only its own accepted prior dialogue, so after-state cannot leak backwards. Include (a) a scorch callback with/without a legitimate setup; (b) an earlier printer disagreement; (c) the autocorrect/spoon motif with an eligible and an ineligible holder; (d) the tunnel example, where a window request changes a safe-entrance proposal; and (e) refusal/anger/quiet. Preserve both successful and rejected samples without retries or cherry-picking.

Score opener clarity, distinct voice, knowledge attribution, whether replies add information/tension, natural length/stopping, and whether a detail matters in a later encounter without spreading unsupported across partners. Judge the rendered chronology as well as model input. Report actual calls, input/output usage, latency, estimates, rejections and uncertainty per arm. Mock success is not evidence of improved live writing, semantic truth, full private-thought isolation or a universal memory system. All accepted speech is public: a fictional confidence is visible in the journal/Gazette and can be copied by readers. Private capture, disclosure consent, visibility-aware retrieval, safe logs and per-resident sessions must be specified before adding durable confidences. A later gossip design should build holder/teller/listener/source-sequence chains without promoting suspicion or repetition to firsthand fact; current `transmissions=[]` remains enforced.
