# V2B follow-up: optional AI provider and private visitor chat

This is a separate proposed PR, not an implemented or promised feature. V2A remains a complete scripted world with zero paid API calls. There is no visitor chat UI, unused API key, model selector, background network job, or half-working provider to enable. The V2A AI flag fails closed if turned on.

## Provider acceptance criteria

- At implementation time, read the OpenAI documentation skill and verify current Responses API structured outputs, supported low-cost models, moderation, token usage, and pricing from official OpenAI sources. Record verification date and direct sources. Do not reuse a guessed model name, stale pricing, or a generic per-token estimate. The model is environment-configurable only within an approved model/pricing allowlist. Unknown model, unknown token usage/cost, missing moderation, or stale/unverifiable pricing must prevent paid execution.
- Keep the feature flag disabled by default. Credentials come only from server-side environment/secrets, never Git, browser code, JSON errors, prompts, event payloads, or logs. Use the fixed official API endpoint with TLS verification, strict timeouts, input/output token limits, no user-controlled URLs/tools, no shell/database tools, and bounded resident traits/public memories as context. No private visitor text may enter public social context.
- Require strict structured outputs with the small reviewed action vocabulary; model responses are untrusted proposals. PHP must independently validate types, allowed actors/targets, ownership, map limits, rate/budget limits, dialogue length/content, and moderation before applying a transaction. Neither success nor fallback can bypass world constraints. Moderate inputs and outputs server-side; on failure use existing curated scripts or decline the interaction. Never let untrusted text become HTML or executable code.
- Add a reviewed schema migration (likely V3) for an application-stored budget ledger and job reservations. V2A usage fields intentionally allow zero only. Enforce explicit daily AND monthly micro-dollar caps atomically before any request, reserving worst-case spend rounded upward from verified input/output pricing and token maxima. Reconcile usage conservatively after completion; retain reservations on unknown outcomes instead of retrying into extra spend. Record model/pricing version, bounded approximate tokens/cost, outcome and safe error codes without prompts/keys. Refuse execution if a cost cannot be determined; no silent fallback to an unpriced model. Handle month/day boundaries and concurrent workers in tests.
- Replace the short V2A transaction lock with a durable, bounded job lease/reservation appropriate for network latency. Do not hold SQLite writes open across a paid request. Prevent overlapping periods and duplicate paid attempts, including timeouts/crashes. Apply validated proposals once using existing event idempotency. Document recovery of uncertain costs/expired leases before enabling the provider.
- Offline tests only by default: mock Responses and moderation transports, schema-valid/invalid outputs, prompt injection, unavailable services, missing usage, stale/unknown prices, timeouts, cap exhaustion, concurrent reservations, month rollover, retries and uncertain outcomes. A real paid smoke test requires explicit owner authorization and a strict spending limit.

## Visitor chat acceptance criteria

- Chat is opt-in and limited to one resident. Before the first message, show what is saved, who can read it, exact retention, and how deletion works. Do not request names, email, location, or other personal information. Warn against sharing private information without collecting it by default. State that the resident is a virtual character and responses may be scripted or generated; avoid suggesting consciousness, confidentiality guarantees, or professional support.
- Use a separate private conversation identity/deletion credential with HttpOnly/SameSite/Secure handling or an equally reviewed no-account mechanism. Do not reuse public profile IDs as authority. No tokens in query strings or storage/telemetry. Strict CSRF, body/turn/token/network/session limits and paid-budget reservations apply. A resident's creator token does not grant access to a visitor's private chat.
- Default to short retention (proposed 24 hours, subject to review) and a clear Delete conversation control that removes messages and any derived private memories. Implement and test an explicit retention command plus operator scheduling approval; do not claim automatic deletion if no job runs. Never append visitor chat to the immutable public journal. Do not leak private messages/memories into public profiles, model social context, exports, or generic debug logs. Review backup retention/deletion limitations before launch.
- Moderate both directions; curate non-cruel, non-harassing behavior, refuse destructive requests, and offer a safe scripted response if the paid provider is disabled/unavailable. No uploads or arbitrary public free-text bubbles. Public world changes, if ever proposed through chat, still require separate explicit visitor action and existing ownership/validation limits.
- Acceptance tests include opt-in/consent UI, keyboard/mobile/reduced motion, stranger/creator access isolation, deletion/retention across all derivatives, no public leakage, abuse and cost caps, injection, provider outages, and offline transport mocks. Ship only when the complete privacy, budget, and moderation flow is reviewable. Otherwise keep this a follow-up plan with no live UI.
