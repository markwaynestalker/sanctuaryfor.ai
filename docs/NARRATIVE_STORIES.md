# Director-authored narrative stories

Individual public conversations remain immutable. Existing short-term continuation receipts remain separate and retain their existing behavior; they are not automatically converted into narrative stories. The optional narrative capability defaults off and requires its own explicit, additive V6 migration on a backed-up, drained database. Migration creates empty append-only story and membership tables; it does not change user_version or backfill historical relationships.

When explicitly enabled in Director dialogue mode, the existing generation request carries a bounded set of candidate stories and an optional structured decision: none, start, continue, conclude, or revisit. Candidates are verified public story heads, not PHP topic matches. If a current participant actually spoke in the supplied exchange, it is attributed to that participant; otherwise it is Director reference only, not a participant memory. Only stories offered in the retained context can be selected. Both participants may be new to a story. Independent Spark mode and custom context providers fail closed while the capability is enabled.

PHP validates the decision and rechecks the offered story head, public source and any claimed actual holder under the existing successful-conversation transaction. Only a completed, moderated conversation can add membership. A conclusion is recorded with an accepted exchange; a later accepted exchange may explicitly revisit it. Quiet, rejected, failed, uncertain, rolled-back, and standalone outcomes create no story link. Membership, transition and ordering records are immutable. No new provider request, scheduler interval, budget, or historical conversation is created or modified.

The archive lists Director-linked stories separately from individual exchanges. Native links open a story and page through up to ten public exchanges at a time, in accepted order, with original speaker names, avatars, words, timestamps, sources and individual archive links. Lists are paginated by ten stories. Public authorization is rechecked for every visible exchange; private or invalid entries and their internal sequence gaps are not exposed. Existing archive filters and individual links remain available. Threads are not inferred from names, dates, topics or short-term lineage.

Local testing uses disposable databases and mock transports only. The migration and `LITTLE_SPARKS_NARRATIVE_STORIES_ENABLED=1` are separate future owner operations; this change does not run a production migration, change production configuration, replace the hosted Director definition, or authorize deployment or paid calls. Provider schema compatibility has only been tested offline.

## Proposal validation and privacy-safe diagnostics

Managed output first passes turn/item identity and envelope checks, bounded JSON decoding, and proposal field validation. The latter checks exact keys, contract and outcome, allowed actions, message count and valid actual speakers, safe original text, note references and exact quotes, bulletin constraints, and the optional narrative decision. Narrative validation then checks the actual offered ID and its open/concluded state; contract and conversation-only checks follow. The entire original proposal is moderated before the existing transactional conversation apply. Story append is part of that transaction and rechecks the public conversation, offered snapshot, witness and current story head. An apply failure rolls back the conversation and story together. No receipt records provider output or context.

PR #113's schema allowed a non-null story ID for `none` and `start`, or a null ID for `continue`, `conclude` and `revisit`, while PHP rejected those values. The schema now expresses the matching action/ID variants, and fresh context states the cross-field rules. Since schema cannot establish the offered snapshot or its changing state, PHP still validates those facts and requires a conversation for a story action. A new managed session scope keeps existing sessions with the old schema separate. Existing `proposal_content` receipts contain no category, so their exact historical cause cannot be established from those receipts alone.

New content-stage receipts contain one fixed category. `proposal_keys`, `proposal_fields`, `topic_text`, `outcome_shape`, `message_shape`, `message_speaker_order`, `message_text`, `message_format`, `duplicate_messages`, `note_shape`, `note_reference`, `note_text`, `note_quote`, `notice_choice`, and `notice_content` identify the corresponding existing validation rule. `narrative_shape_or_action` identifies malformed fields or action; `narrative_unexpected_id` and `narrative_missing_or_invalid_id` identify invalid action/ID combinations; `narrative_requires_conversation`, `narrative_not_offered`, and `narrative_state_mismatch` identify contextual rejection. `contract_mismatch` and `conversation_required` identify final contract and mode checks; `director_fields` and `narrative_decision` are fallback locations. Item-envelope and JSON receipts remain stage-only. Categories never include field values or exception text. Failed managed sessions remain uncertain and their accounting holds are preserved.
