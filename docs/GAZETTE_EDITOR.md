# Gazette editor: architecture and offline contract (#78, first PR)

This is the first of three proposed implementation PRs. It adds an unused, read-only source-pack builder, a draft contract and structural/evidence validation. Nothing calls these helpers from a public route, scheduler or publication command. The deployed compiled Gazette, its private immutable v1 files and all current publication behavior remain unchanged. No provider calls, credentials, ENV, schema migration, accounting or production operation are introduced.

The subsequent inactive ledger foundation and its separately reviewed explicit migration are described in [GAZETTE_EDITOR_LEDGER.md](GAZETTE_EDITOR_LEDGER.md). The original first-PR boundaries above describe that earlier implementation step; the ledger still adds no transport, active job or public AI edition.

The third implementation step is described in [GAZETTE_EDITOR_INTEGRATION.md](GAZETTE_EDITOR_INTEGRATION.md): default-off transport, protected owner tooling and a compatible versioned reader. Paid activation, ledger migration, credential delivery and scheduling remain separate owner operations.

## Editorial model and source selection

The intended editor prepares one draft for a finished America/New_York calendar day. The lead has two to four narrative paragraphs; up to four supporting stories or optional columns have one to four paragraphs each. Thin days may have just a lead; a day without eligible material should use the compiled quiet page without a paid request. Columns follow actual material, never a mandatory resident roster. Editorial prose must distinguish things said, proposals and make-believe from world actions. This initial draft contract deliberately has no verified-world-action claim type.

`editorialSourcePack()` requires an independent SQLite connection already set to `PRAGMA query_only=ON`. One read transaction binds counts, selected conversations and notices to the same snapshot. It uses the existing `gazetteSourceSetup()` / `conversationPublicSource()` authorization and `bulletinPublicSql()` successful-run, actual-author and withdrawal rules. No private notes, memory, operator records, descriptions, Director topics, credentials, run/session IDs or provider bodies are selected. Public AI/scripted attribution remains present.

Complete transcripts include all original messages, ordered sequences and attributed public identities. The collector additionally rejects missing/noncontiguous sequences, more than two speakers, nonalternation, malformed/control text and credential-shaped text. Legacy two-message, odd exchanges and complete extended transcripts through 64 messages work. No saved speech is shortened to fit a source pack. Source dialogue may contain instruction-shaped language; it remains untrusted data. A later API adapter must place editorial instructions separately and must not provide tools or treat source content as commands.

The reporting candidate query is bounded to 256 current-day and 128 background conversations, ranked across first speakers and UTC-hour buckets. Greedy selection then prefers less-covered actual speakers and hours; admitted sources are presented chronologically. This is reproducible diversity, not semantic relevance, exhaustive history or a guarantee of equal resident exposure. Background selection samples a bounded recent candidate pool, not all earlier history. Future editorial evaluation must check whether useful continuing threads survive the sample.

Call arguments, not new ENV settings, currently define these structural bounds:

| Bound | Default | Accepted ceiling |
| --- | --- | --- |
| Edition-day conversations | 64 | 128 |
| Earlier conversations | 12 | 32 |
| Earlier local-calendar days | 3 | 7 |
| Edition-day notices | 8 | 12 |
| Entire serialized source envelope | 131,072 bytes | 262,144 bytes |

Zero disables a source category; bytes must be at least 2,048. Unknown, noninteger and out-of-range settings fail explicitly. Selection admits complete records only, in priority order: today's conversations, notices, then background. A full current-day budget can exclude all background/notices. Notice candidates are bounded to the first 64 authorized daily posts; the same diversity/byte admission applies. Notice text up to 1,000 characters is an unverified author expression; expired posts can be historical evidence of posting, while withdrawn posts are excluded. Markup/control/credential-shaped notice text is excluded rather than altered.

`counts` contains full eligible edition-day totals, while `coverage` separately states how many records were actually supplied. Background never increases today's totals. Counts use the existing Gazette public-source predicate; the added transcript-integrity checks can further reduce the sample. The byte limit is **not a measured provider token count or a provider billing cap**. Exact tokenizer support, complete request-envelope bounds, output allowance and priced reservations must be implemented before any API dispatch. Input must be refused or reduced by dropping whole sources before dispatch if those separate limits cannot be satisfied.

Every record has a local alias plus its public source ID, date, type and edition/background scope. The SHA-256 binds the exact pack, including original names/text, bounds and counts. It excludes wall-clock assembly time so identical completed snapshots are stable across job restarts. This checksum is a binding identifier, not authentication of untrusted files or proof of source authorization. Only the trusted collector's envelope can be passed to validation. In a later persistent workflow, approval/publication/readers must recheck each cited source's current authorization and exact content; a cached pack alone is insufficient. Later additions must not rewrite frozen counts/copy.

## Draft contract and validation boundary

`contracts/gazette-draft-v1.schema.json` describes `sanctuary.gazette.draft.v1`. Every headline and paragraph contains text, an expression category and one to eight message/notice references. Each story must cite edition-day evidence in its prose; background-only articles are rejected. Connections are `standalone`, `theme` or `claimed_continuation`. A claimed continuation requires at least two conversation sources and **still requires human assessment of the connection**. The contract cannot establish that one resident knew about another conversation.

Quotes contain references only. PHP resolves original words and identity from the trusted pack; the model cannot replace a quotation or its attribution. Notices use a null sequence, conversations use the exact sequence. Duplicate references per claim, repeated quotation references, more than two quotes per resident, unknown sources, unknown sequences, replacement quote fields and extra properties are rejected. Copy has separate headline/paragraph bounds, no markup/control characters or credential-shaped strings, and a total 64-KiB draft bound. The first story must be the only lead and contain at least two paragraphs. PHP imposes these contextual rules beyond the static schema. Provider schema acceptance is not tested or claimed by this offline PR.

`validateEditorialDraft()` checks shape, snapshot binding, reference existence and exact quote resolution. It returns only `needs_moderation_and_owner_review`, an exact draft digest, used aliases, resolved quotations and the full headline/paragraph/quote text for future moderation. It never returns approval, writes a draft, moderates, publishes or opens a network connection.

Citation existence does not prove entailment. The test suite intentionally demonstrates that an unsupported sentence paired with a real reference still reaches the mandatory review state. A model's `claim_type` is also untrusted. Review must check headlines as well as prose, proposed versus completed actions, rumor versus fact, changed opinions, implied commitments/relationships and alleged continuity. Moderation is a separate safety check, not a factual verifier. Do not present these checks as automatic factual validation or route their result directly to publication.

## Planned independent generation and financial controls (later PRs)

Prefer one independently budgeted Responses generation for an edition, with no resident-session reuse, tools, browsing, previous-response chain or per-conversation provider calls. The editor's instructions and personality are separate from the hosted Director. No hosted definition change is needed. Structured output constrains shape but not truth; Responses' output-token allowance includes visible and non-visible tokens. See official OpenAI [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) and [token counting](https://developers.openai.com/api/docs/guides/token-counting). Model, tokenizer, rates and endpoint behavior require current verification in the integration PR; no model availability, price or journalistic quality is established here. Reused managed session spending limitations are recorded in [MANAGED_SPEND_CONTROL_REVIEW.md](MANAGED_SPEND_CONTROL_REVIEW.md).

The second PR should propose a separately reviewed, transactional V6 add-on with namespaced editorial attempts, request/usage records, immutable draft revisions and approval/publication events. Do not reuse `ai_attempts`, resident pairs, simulation opportunities, Director session scopes or relationship accounting. Dedicated explicit editorial daily/monthly micro-USD limits and daily request limits must reserve generation plus moderation before dispatch. Reserve worst-case supported input/output costs, including applicable charge categories, without relying on cache discounts. Report actual usage and approximate cost separately from conservative commitments and final billing evidence. Existing Director budgets must remain unchanged; editorial spending is an additional owner allocation, not hidden headroom in the Director's allocation.

Use a separate editorial lease and short SQLite transactions, never a write lock across network calls or the Director's `ai_lease`. Bound lock waits and fail the editor safely rather than block village work. Use UTC dispatch-day/month budget windows separately from the Eastern edition date. Record dispatch before sending, fence expired workers and retain uncertain commitments. Transport uncertainty is not permission for another generation. Bind idempotency to date, source digest, editor contract/policy/model version, **and enforce a separate per-date attempt/revision allowance**, so new snapshots cannot evade the daily generation guard. A cached or previously dispatched attempt cannot be regenerated automatically. Manual later revisions require their own explicit allowance and remaining financial capacity. Moderation failures/retries need equally bounded recorded treatment; no unaccounted retry loops.

## Planned publication, scheduling and recovery (later PRs)

Lifecycle: source snapshot -> reserved attempt -> dispatched -> captured draft -> structural checks -> moderation -> owner factual review -> approved exact draft -> published revision. Failure, refusal, truncation and uncertainty are explicit nonpublication outcomes. Existing compiled editions/previews remain available when generation is disabled or unavailable. An unsafe previously published edition must be withheld under the current source rules; do not silently replace a withdrawn edition with new copy.

Owner approval must bind the exact draft digest, source snapshot and moderation result. Editing any copy requires new validation/moderation and approval. Immutable revisions and an atomic expected-current publication pointer should support corrections/supersession while retaining stable edition URLs and explicit revision links. Never overwrite a Phase 1 `<date>.json` file. Preserve the v1 reader and current source-withdrawal behavior. New v2 reading must validate cross-day sources by their own dates rather than the existing v1 same-day rule. Private draft files/ledger require a consistent backup and recovery plan in addition to SQLite; an orphaned draft must never become public merely because its file exists.

An independently installed, default-off owner-reviewed job could prepare yesterday's draft around 05:15 America/New_York. This is a proposal, not the verified current rest schedule. It changes neither Director cadence nor sleep configuration. Calendar-day selection and duplicate prevention must handle DST and missed jobs without automatic paid backfill. Explicit owner editorial approval means a ready draft, not guaranteed approved publication, by 06:00. The reader should prominently link yesterday's latest approved edition; public GET requests remain query-only and trigger no paid generation, moderation, publication or retry.

## Review boundaries and validation

1. **This PR:** isolated source-pack helper, draft contract, offline structural/evidence tests and this architecture. No active call site or UI change, hence no new screenshots or device claims.
2. **Accounting/storage PR:** explicit schema/backup/rollback review, immutable lifecycle and concurrency/crash tests using mocks. Migration is an owner operation, never automatic on deploy.
3. **Integration/reader PR:** bounded Responses adapter and moderation, protected credential delivery, explicit approval tooling and compatible versioned reader. Offline transports and desktop/tablet/phone/no-JS checks first. Any paid evaluation needs a separately approved request/cost budget and synthetic data; measure story accuracy, diverse coverage, useful continuity and thin-day restraint rather than just successful JSON.

Production activation, ENV, service installation/scheduling, migration, paid evaluation, merge and deployment remain separate owner decisions. Phase 2 is not complete or enabled by this PR. Run `tests/village-gazette.mjs`, `tests/village-bulletin.mjs` and all offline suites; require Ubuntu CI for Linux-only filesystem/locking/deployment checks. Tests cover V2/V6, full 3/16/64-message sources, privacy, instruction-shaped dialogue, byte pressure, sampled counts/diversity, DST, notices, source/draft binding and the deliberate semantic-validation limit.
